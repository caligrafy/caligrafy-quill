# 9.9.7 Phone and Tablet Apps

> Source: Caligrafy Quill wiki - https://github.com/caligrafy/caligrafy-quill/wiki/9.9.7-Phone-and-Tablet-Apps
> Bundled with the caligrafy-quill Claude plugin. Content preserved from the wiki; formatting cleaned.

A Caligrafy project can have its own **iOS and Android app** (Caligrafy Quill 2.27.0+): the same capabilities as its
web pages, REST API and AI agents, on a phone or a tablet, signed in with the same accounts and reached by the same
notifications. One command creates it, one line of `web.php` lets people sign in to it, and the store builds go to
TestFlight and Google Play from a Mac or from GitHub.

With Claude Code, `/caligrafy-quill:mobile` does all of it, and walks you through the Apple and Google accounts. Step
by step: the course's [lesson 18](https://github.com/caligrafy/caligrafy-quill-course/wiki/18-Bookshelf-in-the-Stores)
turns Bookshelf into an iOS and Android app.

## What it is made of

| Part | What it does |
| --- | --- |
| `php caligrafer.php mobile <name>` | Creates `public/<name>`: a Vue app (Vite, Vue Router, Caligrafy's look) that [Capacitor](https://capacitorjs.com) 8 wraps into an Xcode project (`ios/`) and an Android Studio project (`android/`) |
| `Route::mobile([...])` | People sign in to the app through the site's own sign-in page; the app gets a token of that person and calls the capabilities with it |
| `Notify::user()` | The notifications you already send reach the person's iPhones, iPads and Android phones too |
| `fastlane/Fastfile`, `.github/workflows/mobile-<name>.yml` | The store builds: iOS to TestFlight, Android to the internal testing track of Google Play |

The app is never a second backend: every screen reads and writes through the project's capabilities, as the person
signed in, under the same rules (scopes, levels, validation) as the web pages, REST and MCP.

## Create it

Node.js 22+ on your computer (the Docker server has none), then at the root of the project (from the Docker server,
`docker compose exec dev-box php caligrafer.php mobile ...` with `--id` and `--url`, then the `npm` and `npx cap` lines
it prints, on your computer):

```bash
php caligrafer.php mobile bingo --id com.holidaybingo.app --display "Holiday Bingo" --url https://holidaybingo.caligrafy.com
```

+ `--id`: the app id. It is the bundle id of iOS, the package of Android and the address the sign-in returns to the
  app through. Lowercase letters and digits in two or more parts separated by dots (no `-` or `_`). It cannot change
  once the app is in a store. Default: `com.<project folder>.<name>`.
+ `--display`: the name under the icon (30 characters). Default: the folder's name.
+ `--url`: the site the store builds call. Default: `APP_URL` when it is https, else `https://<project folder>.caligrafy.com`.

It installs the packages, adds the iOS and Android projects, sets up their sign-in address and notifications, makes the
icons from the Caligrafy mark (replace `assets/icon-only.png` and run `npm run icons`), and writes the GitHub workflow.

## Sign people in

In `application/config/routing/web.php`, after `Route::auth()` and `Route::capabilities()`:

```php
Route::auth(['home' => '/']);
Route::capabilities('/capabilities');
Route::mobile(['scheme' => 'com.holidaybingo.app']);
```

1. The app opens `https://<site>/mobile/authorize` in the phone's browser.
2. The person signs in on the site's own page, or creates an account, then allows the app on that device.
3. The site sends them back to the app with a one-time code. The app trades the code for a personal access token of
   that person: "Mobile: Maya's iPhone" in the tokens list.

A project without accounts (2.27.2+) keeps the same line: it then declares no sign-in address and only lets its apps
call the public capabilities, with no sign-in and no token.

The app never sees a password. The exchange is protected with PKCE, so a code is useless to any other app that
intercepts it. Signing out of the app revokes the token.

| Option | Default | |
| --- | --- | --- |
| `scheme` | (required) | The app id (or a list of ids, one per app) |
| `scopes` | `['*']` | What the app may call. `['*']` is whatever the person may do; narrow it with `['books:read', 'books:write']` |
| `days` | `90` | How long the app stays signed in |
| `origins` | `[]` | Other origins allowed to call with a token (the app's own are always allowed) |
| `name` | `APP_NAME` | The app's name on the consent page |

The routes: `GET`/`POST /mobile/authorize`, `POST /mobile/token`, `GET /mobile/session`, `POST /mobile/signout`.

## Build its screens

`src/components/pages/` and `src/router/index.js`. A page reads and writes through `call()`:

```js
import { call } from '../../mobile/session.js'

const books = await call('list_books', { page: 1 })
try {
  await call('create_book', { title: this.title })
} catch (error) {
  this.errors = error.fields      // { title: 'The Title field is required' }
}
```

`currentUser()`, `signIn()`, `signOut()` and `onSessionChange()` come from the same file. A `webOnly: true` capability
needs the browser's session, so the app cannot call it: give the app a capability of its own.

```bash
npm run dev        # in a browser, against the Docker server (sign-in works the same, on this computer only)
npm run ios        # a development build, then Xcode: run it on an iPhone simulator
npm run android    # the same in Android Studio: an Android emulator
```

These development builds call your local site (`.env.development`, `http://localhost:8080`): the iPhone simulator
reaches it at `localhost`, the Android emulator at `10.0.2.2` (the app switches by itself), and plain http is allowed
to this computer's addresses only. The store builds, `npm run release:ios` and `npm run release:android`, call the site
online (`.env.production`, https); the workflow and fastlane use them. To try the app on a real phone, use a release
build against the site online.

Tested on an iPhone 18 Pro simulator (iOS 27.2) and a Pixel emulator (Android 16): sign-in through the site, the
return to the app, a restart, notifications turned on and shown, and sign-out.

## Notifications

The `Notify::user($id, ['title' => ..., 'body' => ..., 'url' => ...])` you send for the browsers and email
([Notifications](https://github.com/caligrafy/caligrafy-quill/wiki/Notifications)) reaches the phones once the person turns them
on in the app (`enablePush()`), with these settings on the site:

| Setting | Where it comes from |
| --- | --- |
| `APNS_KEY`, `APNS_KEY_ID`, `APNS_TEAM_ID` | Apple Developer, Keys: a key with Apple Push Notifications service (the `.p8` text, or that text in base64), its id, your team id |
| `APNS_TOPIC` | The app id |
| `APNS_ENVIRONMENT` | `sandbox` while you run the app from Xcode; leave it out for TestFlight and the App Store |
| `FCM_SERVICE_ACCOUNT` | Firebase console, Project settings, Service accounts: the private key's JSON (or that JSON in base64) |

In the app: the Push Notifications capability in Xcode (Signing & Capabilities, once), and
`android/app/google-services.json` from Firebase for Android. Check with `php caligrafer.php notify status <user id>`
and `php caligrafer.php notify test <user id>`. Online, set them with `php caligrafer.php cloud secret set <app> NAME=value`.

## Publish it

What you do once, as the owner of the accounts:

1. **Apple**: the [Apple Developer Program](https://developer.apple.com/programs/enroll/) (99 USD a year), the app in
   App Store Connect, and an App Store Connect API key with the Admin role. Xcode signs the builds with that key:
   there is no certificate or provisioning profile to keep.
2. **Google**: a [Google Play developer account](https://play.google.com/console/signup) (25 USD once), the app in
   Play Console, an upload key (`keytool`), and a service account allowed to release. Google needs the first build
   uploaded by hand. A new personal account must also run a closed test with 12 testers for 14 days before its first
   production release.
3. **The secrets of the repository** (GitHub, Settings, Secrets and variables, Actions): `APPLE_TEAM_ID`, `ASC_KEY_ID`,
   `ASC_ISSUER_ID`, `ASC_KEY_P8`, `ANDROID_KEYSTORE`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`,
   `ANDROID_KEY_PASSWORD`, `PLAY_SERVICE_ACCOUNT` and, for Android notifications, `GOOGLE_SERVICES_JSON`. The README of
   `public/<name>` says where each one comes from.

Then each release: change `version` in `public/<name>/package.json`, push, and run the workflow (`/caligrafy-quill:ship`
does it, or `gh workflow run mobile-<name>.yml -f platform=both`). iOS arrives in TestFlight, Android on the internal
testing track; you send it to review from App Store Connect and Play Console. On a Mac with Xcode, the same lanes run
locally: `bundle exec fastlane ios beta`, `bundle exec fastlane android beta`.

Before the first review: Apple asks an app with accounts to let people delete their account inside the app, a
privacy policy address and the privacy labels; both stores ask for screenshots.
